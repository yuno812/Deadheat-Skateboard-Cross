# DSC CPUシミュレーター仕様書

Nov 2, 2026 · @NazEt

## 目的と範囲

CPUプレイヤーの判断ロジックを、Unityより桁違いに速いRust製ヘッドレスシミュレーターで統計を取りながら調整する。シミュレーターの結果を信用できるように、同じ入力をUnityでも再生して数値を照らし合わせる。

**v1でやること**

- 1ステージ（R2500：多角形の地面1枚だけの最も単純なステージ）と全8キャラ
- `MovePlayer` の移動・回転・ジャンプ・場外判定・ダメージ判定
- 通常／チャージ中で当たり判定が切り替わる処理
- 照合用シナリオの再生と比較、復帰・ジャンプ・対戦のCPU調整実験

**v1でやらないこと**

- ウルト（キャラごとの別処理。v2で追加）
- ステージの仕掛け：重力反転、ジャンプ強化エリア、バンパー、動く床、フリッパー（v2以降）
- 毎ステップ単位での完全一致（物理の誤差は増幅するため、数値の統計で合否を判断する）
- 機械学習。必要になれば、同じシミュレーターの上に後から載せる

## 全体構成

Unityで形と値を書き出し、同じシナリオをUnityとRustの両方で再生して照合する。合格してから、RustでCPUを調整してC#へ移す。

## Unity側①：形状とパラメータの書き出し

シミュレーターが使う値は、すべてUnityから自動で書き出す。手で写すと必ずずれるため。ファイルは `export/<ステージ>_<P1キャラ>_<P2キャラ>.json`。

**書き出すタイミング**：ステージシーンを実際に起動し、最初のFixedUpdateの時点で書き出す。理由は次の3つ。

- `GameManager.Awake` がキャラを生成し、`playerScale`（シーンごとの値）を掛ける
- `MovePlayer.Awake` が `rb.mass` を `PlayerState.weight` で上書きする（Prefab上の値は1）
- P2はY軸180°に回転して左右反転している。反転後の形を取る必要がある

**形の取り方**：`PolygonCollider2D` の頂点をそのまま使わず、`Collider2D.GetShapes(PhysicsShapeGroup2D)` で「物理エンジンが実際に使っている凸形・円」を取り出す。Unityが内部で行う凸分割を、Rust側で再現しなくて済む。座標系は「キャラは自分のRigidbody2Dのローカル、ステージはワールド」とする。

**書き出す項目**

| 対象 | 項目 |
| --- | --- |
| ワールド | 重力、`fixedDeltaTime`、Physics2D設定一式（反復回数、Baumgarte、接触オフセット、最大並進・回転、スリープ設定）、レイヤー衝突マトリクス |
| キャラの剛体 | 質量、慣性モーメント（`rb.inertia`）、重心（`rb.centerOfMass`）、重力スケール、減衰（並進・回転）、衝突検出モード、初期の位置と角度 |
| キャラの当たり判定 | 形状ごとに：タグ（`TireCollision` / `MainCollision` / `AttackCollision`）、トリガーかどうか、所属する姿勢（`Normal` / `Charge` / `Ult` / 常時）、摩擦、反発、それぞれの合成方法、レイヤー |
| キャラの能力値 | `PlayerState` の全項目（`maxSpeed`、`moveForce`、`jumpForce`、`rotationTorque`、`attack`、`hp`、`ultAmount`）、`ultGainMultiplier` |
| ステージ | 当たり判定（上と同じ項目。`Ground` タグも含む）、P1とP2のスポーン地点、場外の境界（`outofArea`） |

形式の例（抜粋）：

```json
{
  "schema": 1,
  "unity": "6000.1.14f1",
  "world": { "gravity": [0, -9.81], "dt": 0.02, "velocityIterations": 8, "positionIterations": 3, "baumgarte": 0.2, "contactOffset": 0.01 },
  "players": [{
    "slot": 1, "character": "zero", "mirrored": false,
    "body": { "mass": 0.55, "inertia": 0.0, "com": [0, 0], "gravityScale": 1, "linearDamping": 0, "angularDamping": 0.05, "pos": [0, 0], "angleDeg": 0 },
    "stats": { "maxSpeed": 5, "moveForce": 0, "jumpForce": 9, "rotationTorque": 3, "attack": 0, "hp": 0, "ultAmount": 0, "ultGainMultiplier": 5 },
    "shapes": [{ "pose": "Normal", "tag": "TireCollision", "trigger": false, "kind": "circle", "center": [0.44, -0.72], "radius": 0.115, "friction": 1, "bounciness": 0 }]
  }],
  "stage": { "name": "R2500", "spawn": [[-3, 0], [3, 0]], "outOfArea": [12, 8], "shapes": [] }
}
```

上の数値は形式を示すための仮の値で、実測値ではない。

## Unity側②：シナリオ再生とトレース記録

照合の「正解」を作る部分。シナリオファイルをUnityで再生し、毎ステップの状態を記録する。**ゲーム本体のコード（`MovePlayer` など）は変更しない**。追加するのは入力用のクラス1つと、記録用のテストだけとする。

**シナリオの形式**（Rust側と共通。シナリオは主にRust側で生成し、同じファイルを両方で再生する）

```json
{
  "id": "S6-zero-upsidedown-rotL",
  "stage": "R2500", "p1": "zero", "p2": "hitsuji",
  "steps": 250,
  "init": [{ "slot": 1, "pos": [0, 1.5], "angleDeg": 180, "vel": [0, 0], "angVelDeg": 0 }],
  "inputs": [
    { "slot": 1, "from": 0, "to": 250, "moveX": 0, "rotate": 1, "jump": false }
  ]
}
```

- `inputs` は区間ごとに書く（`from` 以上 `to` 未満のステップ）。書かれていないステップは入力なし
- `ultimatePressed` など「押した瞬間」の入力は、v2でイベントとして追加する
- `init` を省略したプレイヤーはスポーン地点から始める

**入力の差し込み**：`ScriptedInputProvider : IInputProvider` を `InputManager.inputP1` / `inputP2` に入れる。`GetInput()` はFixedUpdateとUpdateの両方から何度も呼ばれるため、呼ばれた回数ではなく、**物理ステップの番号**（`Time.fixedTime` を `fixedDeltaTime` で割って丸めた値）を見て入力を返す。

**実行の流れ**（Unity Test FrameworkのPlayModeテスト、1シナリオにつき1ケース）

1. `Time.captureDeltaTime = fixedDeltaTime`（0.02）にする。1フレームごとに物理ステップがちょうど1回進み、実時間を待たずに最速で回る
2. `InputManager` と `PlayerSelection` がなければ作る。キャラ名からPrefabを引く対応表で `playerPrefabP1` / `P2` を設定する
3. ステージシーンを読み込む。`GameObserver` は無効にする（HP0でResultSceneへ移って記録が途切れないようにするため）
4. 最初のステップの前に `init` を反映する（`rb.position`、`rb.rotation`、`rb.linearVelocity`、`rb.angularVelocity`）。同じタイミングで①の書き出しも行う
5. `WaitForFixedUpdate` で毎ステップ待ち、物理計算と衝突コールバックが終わった後の状態を記録する

コマンドの例：

```
Unity.exe -batchmode -nographics -projectPath <プロジェクト> -runTests -testPlatform PlayMode -testFilter DscSim.Trace -logFile trace.log
```

シナリオの入力先と出力先は、環境変数 `DSC_SCENARIOS` と `DSC_TRACE_OUT` で渡す。

**記録する値**（CSV、1シナリオ1ファイル、1行＝1ステップ×1プレイヤー）

| 列 | 内容 |
| --- | --- |
| `step`, `slot` | ステップ番号、プレイヤー番号 |
| `x`, `y`, `angle` | 位置、角度（`transform.up` とワールドの上方向がなす角。度、-180〜180） |
| `vx`, `vy`, `w` | 速度、角速度（度/秒） |
| `ground` | `groundWheelCount`（privateなのでリフレクションで読む） |
| `pose` | 通常／チャージ／ウルト（子オブジェクトの `activeSelf` から判断） |
| `hp`, `ult` | HP、ウルトゲージ |

**再現性の確認**：同じシナリオを2回流し、トレースが完全に一致することを確かめる。Physics2Dのマルチスレッドは無効（`useMultithreading: 0`）なので、同じマシンでは一致する見込み。一致しなければ、照合の許容範囲をそのばらつきに合わせて広げる。

## Rustシミュレーター

置き場所は `C:\Users\hiro-\source\repos\rust\dsc-sim`（cargoのワークスペース）。目標速度は、1コアあたり毎秒5万ステップ以上（実時間の1000倍）。これを全コアで並列に回す。

**クレートの構成**

| クレート | 役割 |
| --- | --- |
| `dsc-core` | 書き出しJSONからワールドを組み立て、`MovePlayer` の移植を含めて1ステップ進める。グローバルな状態を持たない |
| `dsc-scenario` | シナリオの形式、照合用シナリオとランダムシナリオの生成、トレースCSVの読み書き |
| `dsc-ai` | CPUの判断（状況を受け取って入力を返す）と、角度制御・ジャンプ予測などの部品 |
| `dsc-cli` | コマンド：`gen`（シナリオ生成）、`run`（シナリオ再生→トレース）、`compare`（Unityとの照合レポート）、`sweep`（パラメータ探索）、`bench`（速度計測） |

**物理エンジンの要件**

- Box2D v2系と同じ解き方をすること：逐次インパルス法、ウォームスタート、速度の反復／位置の反復を分けて指定できる、Baumgarte、摩擦の合成（幾何平均）、反発の合成（最大値）
- 書き出した値をそのまま渡せること：質量、慣性モーメント、重心を上書きできる。形状ごとに摩擦と反発を持てる
- 接触の開始・終了イベントと、トリガーの出入りイベントを取れること
- 形状の有効／無効を切り替えられ、無効にしたときに「接触終了」が出ること（Unityの設定が `callbacksOnDisable: 1` のため）
- 候補：Box2D 2.4のRust移植、C++版Box2D 2.4へのバインディング、rapier2d（解き方が違うため最後の手段）。照合シナリオS1〜S5に合格したものを採用する

**単位の変換**：Unityの角度と角速度は「度」、Box2Dは「ラジアン」。入出力とトレースは度で統一し、変換は `dsc-core` の境界でだけ行う。`AddTorque` のトルクがUnity内部でどう扱われるかは未確認のため、照合シナリオS5で実測して係数を決める。

**1ステップの処理順**（Unityの実行順をそのまま再現する。各プレイヤーはP1→P2の順）

1. **場外判定**：`|x| ≥ |outOfArea.x|` または `|y| ≥ |outOfArea.y|` なら、HPを1減らし、スポーン地点へ移し、速度を0にする。**角度と角速度は戻さない**（元のコードどおり）
2. **ウルトゲージ**：前回の位置からの移動量と、相手方向の単位ベクトルの内積が正なら、その値×`ultGainMultiplier` を加え、`ultAmount` で頭打ちにする
3. **入力を取る**
4. **姿勢の切り替え**：前のステップのチャージ状態に従い、通常／チャージの当たり判定を有効にする。切り替わると接触の終了と開始が起き、接地カウントも増減する
5. **HPが0より大きいときだけ操作を反映する**
   - 前後移動：`dir = P1 ? moveX : -moveX`。接地中なら、`dir ≠ 0` のとき `vx += dir × moveForce × dt`、それ以外は `vx` を `moveForce/10 × dt` ずつ0に近づける。**空中でも** `vx` は ±`maxSpeed` に制限する（ワールドのx方向であり、坡の向きではない）
   - 回転：`rotate ≠ 0` なら `sign(rotate) × rotationTorque` のトルクを掛ける。その後、角速度を ±900度/秒に制限する（制限は物理計算の前。そのステップのトルクで少し超えることがある）
   - ジャンプ：押し始めたらチャージ開始。離したとき接地していれば `v += up × jumpForce`。どちらの場合もチャージは終了
6. **物理ステップ**（dt = 0.02）
7. **接触イベントの処理**
   - 車輪（`TireCollision` の形状）と `Ground` の接触開始／トリガー進入 → 接地カウント+1、終了／退出 → -1（0未満にはしない）
   - 自分の体 × 相手の体、自分の板 × 相手の板 → 自分の速度を「相手から自分への向き × 10」に置き換える
   - 自分の体 × 相手の板 → 速度を「向き × 25」に置き換え、HPから相手の `attack` を引く
   - 自分の板 × 相手の体 → 速度を「向き × 25」に置き換える（ダメージなし）
   - 「向き」は両者のルート（剛体）の位置から計算する。当たり判定の組ごとに発生するので、1ステップに複数回起きうる

**判断部分との境界**

```rust
pub struct Observation {
    pub step: u32,
    pub me: BodyObs,          // 自分
    pub opp: BodyObs,         // 相手
    pub gravity_up: Vec2,     // 重力の逆向き（重力反転ステージ用）
    pub bounds: Vec2,         // 場外の境界
}
pub struct BodyObs {
    pub pos: Vec2, pub vel: Vec2,
    pub angle_deg: f32,       // gravity_up 基準、-180..180
    pub ang_vel_deg: f32,
    pub ground_count: u8, pub pose: Pose,
    pub hp: f32, pub ult: f32, pub ult_max: f32,
    pub facing: f32,          // P1 = +1, P2 = -1
}
pub struct Input { pub move_x: f32, pub rotate: f32, pub jump: bool, pub ult: bool }
pub trait Policy { fn act(&mut self, obs: &Observation) -> Input; }
```

乱数は試合ごとに種を渡す。同じ種で同じ結果になることを保証し、統計の外れ値をあとから再生できるようにする。

## 照合

全キャラで下のS1〜S11とランダム照合R1に合格したら、シミュレーターをCPU調整に使ってよい。比べるのは2段階。

1. **最初の10ステップは厳密に比べる**：位置の差 0.001未満、角度の差 0.1°未満。誤差が増える前なので、ここでずれるなら単位・質量・処理順のどれかが間違っている
2. **それ以降は結果の数値で比べる**：下の表の指標が許容範囲に収まるか

| ID | シナリオ | 確かめること | 指標と許容範囲 |
| --- | --- | --- | --- |
| S1 | スポーン地点で入力なし、3秒 | 落下、着地、静止 | 静止位置 ±0.02、接地カウントが一致 |
| S2 | 平地で前進を押し続け、4秒 | 加速と最高速度 | 最高速度に届くまでの時間 ±3% |
| S3 | 平地でジャンプを10ステップ押して離す | ジャンプの初速と重力 | 最高点の高さ ±3%、滞空時間 ±1ステップ |
| S4 | ±20°・±40°に傾けてジャンプ | 板の向きと飛ぶ方向 | 着地点のx ±5% |
| S5 | 空中高くで回転を1秒押し続ける | トルクの単位、慣性モーメント、900度/秒の制限 | 角加速度 ±2%、制限に届くステップ ±1 |
| S6 | 地上で逆さまから左／右回転を5秒 | 起き上がれるか | 成否が一致、起き上がるまでの時間 ±10% |
| S7 | 地上で横倒し（±90°）から回転 | 同上 | 同上 |
| S8 | 2体を向かい合わせて前進 | 体と板の接触の種類、跳ね返り | 接触の種類と発生ステップ ±1、HPの変化が一致 |
| S9 | P1をP2の真上から落とす | 踏みつけでダメージが入るか | ダメージの有無と発生ステップ ±1 |
| S10 | 端に向けて前進し続ける | 場外判定とスポーン地点への移動 | 場外になるステップ ±2、HP-1 |
| S11 | ジャンプを押しっぱなしにする | 姿勢の切り替えで接地カウントが変わるか | 接地カウントの推移が一致 |

**R1（ランダム照合）**：初期角度と入力列をランダムにしたシナリオをキャラごとに1000本作り、両方で流す。個々の軌道ではなく、分布を比べる。起き上がり成功率の差は5ポイント以内、最高点・着地点の中央値の差は5%以内とする。

**レポート**：`dsc compare` が「シナリオ × キャラ」ごとの合否、差、最初にずれたステップをMarkdownで出力する。不合格のときは、単位→質量と慣性モーメント→摩擦の合成→処理順の順に疑う。

許容範囲は最初の目安。Unity同士で2回流したときのばらつき（「再現性の確認」）を見てから最終的に決める。

## CPU調整

最初に「倒れた状態から回転だけで起き上がれるか」（E1）を調べ、その結果で復帰処理の作り方を決める。その後、部品ごとに調整してから対戦で評価する。

**CPUの構成**（`dsc-ai`）：状況を読む → 行動を決める（場外回避／立て直し／防御／空中攻撃／ジャンプ攻撃／接近の優先順）→ 操作に変える（角度制御、ジャンプの押す→離す）→ 難易度（反応の遅れ、ブレ）。調整する数値はすべて設定ファイル（TOML）に出し、コードに埋め込まない。

| ID | 実験 | やり方 | 決めるもの・目標 |
| --- | --- | --- | --- |
| E1 | 回転だけで起き上がれるか | 各キャラを地上で90〜180°（5°刻み）に傾け、左右それぞれ5秒回転を押し続ける | 「角度 × 方向」ごとの成否と時間。起き上がれないキャラがいれば、揺らして起き上がる処理を入れる |
| E2 | 復帰処理の数値探索 | 効きの強さ、行き過ぎ防止の強さ、何もしない角度の幅、切り返しの条件、時間切れをランダム探索 | キャラごとに、成功率99%以上で復帰時間の中央値が最小になる組 |
| E3 | 着地合わせ | 空中のランダムな位置・速度・角度から、地面の傾きに板を合わせる | 車輪から着地できる割合。目標95%以上 |
| E4 | ジャンプ予測の精度 | 放物線の式で出した軌道と、実際に飛んだ軌道を比べる | 誤差の分布。大きければ補正を加えるか、シミュレーターで先読みする方式に変える |
| E5 | 対戦 | CPU対基準の相手（何もしない／ランダム／突進しかしない）、CPU同士。8×8のキャラの組み合わせで各数百試合 | ランダム相手に勝率95%以上。特定のキャラだけ極端に強い／弱い組を見つける |
| E6 | 難易度 | 反応の遅れとブレを変え、基準のCPUとの勝率を測る | 「よわい／ふつう／つよい」の3組。上の難易度が下に65〜80%で勝つようにする |

**結果の出力**

- 試行ごとに1行のCSV：実験ID、キャラ、数値の組のハッシュ、乱数の種、勝敗、試合時間、与えた／受けたダメージ、場外の回数、倒れていた時間の合計など

## C#への移植とゲームへの組み込み

Rustで決まった判断ロジックをC#へそのまま移し、**共通のテストデータで両方が同じ入力を返すこと**を保証する。

**移植のルール**

- 構造と名前をRustとそろえる（`Observation`、`BodyObs`、`Policy.Act`）
- 調整した数値（TOML）は、同じ項目名のScriptableObject（`CpuProfile`、難易度ごとに1つ）に変換して取り込む
- 乱数は同じアルゴリズム（PCG32など）を両方で自前実装し、`System.Random` や `UnityEngine.Random` は使わない
- **テストデータ**：Rustが「状況、判断前の内部状態、期待する入力」をJSON Linesで書き出し、UnityのEditModeテストでC#版に同じ状況を与えて比べる。回転・ジャンプなどの入力は完全一致、途中の数値は小さな誤差を許す

**ゲーム側の部品**

- `CpuController`（MonoBehaviour）：CPUのキャラに付ける。`[DefaultExecutionOrder(-100)]` で `MovePlayer` より先にFixedUpdateで動き、1ステップに1回だけ判断する
- `CpuInputProvider : IInputProvider`：最後の判断結果を返すだけ。何度呼ばれても同じ値を返す
- ウルトの入力：`MovePlayer` はUpdateで受け付けるため、1フレームに物理ステップが2回入ると取りこぼす。ゲージが0に戻る（＝発動した）まで、最大10ステップ `ultimatePressed` を出し続ける
- `MovePlayer` への変更は、接地カウントと姿勢を読むための読み取り専用プロパティの追加だけにとどめる

**画面の流れへの組み込み**

| 場所 | 変更 |
| --- | --- |
| デバイス選択（`DeviceSelectionManager`） | P2に「CPU」の選択肢と難易度を追加 |
| `InputManager.ApplySelectedDevices` | `"CPU"` のとき `inputP2` に `CpuInputProvider` を入れる |
| キャラ選択（`SelectCharacter`） | CPU側はランダムにキャラを選んで自動で決定する |
| `GameManager` | P2がCPUなら、生成したキャラに `CpuController` を付け、自分と相手の参照と `CpuProfile` を渡す |
| リザルト | 必要なら「2P」の代わりに「CPU」と表示 |
| LAN対戦 | CPUは使えないようにする |
